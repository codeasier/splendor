# 当前主题风格分析

分析日期：2026-11-11。

第 1–10 节记录 `59d8efa` 的初始主题分析；第 11 节为架构决策，第 12 节记录多主题实现，第 13 节记录卡名与调研，第 14 节记录 AI 图集重绘。

## 1. 分析基线

- 独立工作区：`.worktrees/theme-analysis`；分支：`analysis/theme-style`。
- 基于 `feat/wechat-login` 的已提交版本 `59d8efa`。

## 2. 一句话定位

**文艺复兴皇家珠宝商会风格，以酒红丝绒、古金雕花、青绿皮革与油画卡面，营造可触摸的 2.5D 实体桌游体验。**

核心关键词：宫廷、典藏、珠宝、暖光、金属包边、厚纸卡牌、商会仪式感。

首页负责展示珠宝与商会世界观；房间负责展示席位和准备状态；牌桌负责承载规则信息与实体操作。三者共享酒红、金色、象牙白文字与暖光阴影，主题方向明确。

材质通过多层线性 / 径向渐变、内外阴影、重复细纹、SVG 切面和 JPEG 贴图组合表现。卡牌保留纸叠侧壁，筹码保留彩色侧壁，金框同时有高光、倒角和接触阴影。

视觉主光约定为左上暖光，投影整体向下或右下。页面样式开头已有这套约定，后续维护可以直接沿用。

需要区分两套颜色语义：五色宝石加黄金属于游戏资源；青蓝、绿色、橙红属于交互状态。金色同时承担装饰、主要动作与黄金支付提示，应结合位置和文字一起辨认。

## 4. 字体与信息层级

- 品牌名、弹窗标题与部分卡名使用 `Songti SC / STSong / Noto Serif CJK SC / Georgia / serif`，形成典藏和书卷感。
- 分数、筹码数量与房间号大量使用 Georgia 粗体；卡面声望额外使用斜体，强化实体牌的数值特征。
- 正文、昵称与多数操作说明继承系统无衬线字体，以便承载密集信息。
- 大标题使用较大的字距、暖金文字和下沉阴影，和首页雕花板保持一致。
- 字体依赖系统回退；工程没有内嵌字体定义，不同平台的最终字形仍需分别确认。

目前层级跨度较大：首页品牌名为 46 舞台 px，快速开始为 36 px；牌桌卡名为 9 px，回合副文案为 8.5 px。主题气质统一，但手机上的局内文字明显偏小。

### 手机尺寸实测

在 H5 预览的 `844×390` CSS px 视口中，舞台缩放约为 `0.696429`。

| 项目 | 样式字号 / 尺寸 | 仅按舞台缩放后的值 |
| --- | --- | --- |
| 卡名 | 9 px | 约 6.27 CSS px |
| 对手资源数字 | 12 px | 约 8.36 CSS px |
| 回合副文案 | 8.5 px | 约 5.92 CSS px |
| 主按钮文字 | 实际计算样式 11 px | 约 7.66 CSS px |
| 选择原因说明 | 9.5 px | 约 6.62 CSS px |
| 主按钮高度 | 40 px | 实测约 27.86 CSS px |
| 右上圆按钮 | 31×31 px | 实测约 21.59×21.59 CSS px |

卡牌另有自身透视和缩放，所以表中的卡名字号不是最终投影高度，实际会进一步受变换影响。这里的单位是浏览器 CSS px，不是设备物理像素。

另有一个层叠细节：`.pick-main` 声明 13 px，但后面的同等优先级 `.btn` 将其覆盖为 11 px。调整局内字号前应先明确通用样式和组件样式的覆盖顺序。

## 5. 布局与空间语言

舞台固定为 **1080×560**，通过整体等比缩放适配窗口。竖屏窗口会把横屏内容旋转 90°；H5 通过外层 `#frame` 旋转，原生页面通过布局计算处理。

| 区域 | 主要组织方式 | 视觉作用 |
| --- | --- | --- |
| 首页 | 左侧珠宝陈列、顶部品牌、右侧操作板、底部导航 | 强化世界观，突出快速开始 |
| 房间 | 顶部房号、中央大席位卡、底部配置与开始 | 清楚表达谁已加入、谁已准备 |
| 牌桌顶部 | 对手摘要、回合提示、工具入口 | 把其他玩家与当前状态集中展示 |
| 牌桌左侧 | 预留卡槽、三组厚牌叠 | 模拟伸手取牌与收纳的位置 |
| 牌桌中央 | 三行四列发展卡 | 使用单灭点透视，远端收窄、近端展开 |
| 牌桌右侧 | 筹码柱、贵族画廊 | 区分公共资源与目标奖励 |
| 牌桌底部 | 身份 / 资源 / 操作三段工作台 | 把自身状态和确认动作放在一起 |

2.5D 主要由 `perspective`、`rotateX`、`skewX`、逐行缩放与多层阴影完成。卡牌文字与图面一起参与透视，因此获得实体感的同时也承担了可读性成本。

整体缩放保住了完整桌面构图，但没有针对小屏重新分配信息空间。竖屏实测可以看到完整旋转牌桌，阅读方向仍是横屏游戏的方向。

## 6. 美术来源与实现边界

- 首页 `scene.jpg / panel.jpg / merchant.jpg` 来自用户提供的商会大厅参考图；操作文字、玩家资料和按钮文字由 WXML 实时渲染。
- 90 张发展卡缩略图与 10 张贵族肖像采用工程记录的 CC0 油画素材，分别位于 `preview/thumbs/cards/` 和 `preview/thumbs/nobles/`。
- 宝石切面、筹码、牌背、工作台和多数导航图标由 `preview/art.js` 生成 SVG，再与 JPEG 一起内嵌进 `pages/index/art.wxss`。
- `preview/lobby-art.js` 提供首页场景和操作板的程序化兜底；当前素材齐全时实际优先使用 JPEG。
- `index.html` 由 `preview/build.js` 从同一套 WXML、WXSS 和页面逻辑生成。

实际观感中，首页陈列的卡背和筹码更接近高精度写实渲染，局内筹码和牌背更接近简化矢量绘制。色调一致，但纹理、细节密度和高光强度存在落差。

首页底图在左侧窗景处仍能看到横向拼接 / 修补边界。右侧大面积修补区被操作板覆盖后较不显眼，左上窗景的接缝仍值得后续精修。

## 7. 交互与动效

- 卡牌和筹码选中时抬升并出现青蓝光环；按压按钮时向下位移，模拟实体反馈。
- 可直接购买为绿框，需要黄金补齐为金框；选中状态另用青蓝框区分。
- 购买、拿取和贵族到访采用约 1750 ms 的三段展演：从原位置取出、中央悬停、飞入对应席位。
- 换手提示约 1700 ms，弹窗出现约 180 ms；临近超时和退还筹码使用脉冲提醒。
- 展演与换手提醒采用 `pointer-events: none`，保持牌桌的点击通路。
- 当前没有低动态偏好分支；密集操作时是否需要缩短展演，可作为后续体验优化项。

主工作区尚未提交的聊天界面延续了酒红底、金边和青绿自发气泡；大表情使用系统 Emoji 和弹跳旋转动画，比现有商会主题更活泼。此项仅做源码补充观察，未在本分析分支运行。

## 8. 优点与优化优先级

### 值得保留

1. 商会世界观清晰，首页陈列有辨识度，主要动作足够突出。
2. 卡牌、筹码、席位与工作台共享材质语言，有完整实体桌游感。
3. 方形永久折扣与圆形持有筹码形成形状区分，同色资源按列对齐。
4. 当前回合结合青蓝描边与文字提示；准备状态结合颜色与文字，信息表达不只依赖颜色。
5. 美术生成、页面样式和预览构建有明确入口，可在现有架构内渐进改进。

### 优先级 A：先改善局内阅读和操作

- 以缩放后的字号和点击区域为准重新设定手机端最低尺寸，优先处理回合信息、对手数字、确认按钮和工具入口。
- 保留装饰与卡牌透视，将关键数值、状态标签和确认动作放到更稳定、清晰的阅读层。
- 减轻卡牌数值周围的纹理和多重描边竞争，尤其是小型贵族需求数字。
- 明确 `.btn` 与各组件按钮的覆盖关系，避免组件字号被后续通用规则覆盖。

### 优先级 B：统一素材精度与图标语言

- 对齐首页和局内的筹码厚度、卡背纹理、金属反光与色彩饱和度。
- 精修首页底图窗景接缝。
- 把好友字符图标、牌桌字符入口与已有 SVG 导航图标统一到同一套轮廓和尺寸规则；新增聊天 Emoji 也需要统一展示边界。

### 优先级 C：沉淀主题规则

- 把色彩角色、字体层级、边框、阴影与状态定义收敛成可复用的主题参数。
- 当前颜色和材质大多硬编码在样式和美术生成器内；已有 CSS 变量主要承担动画坐标，没有独立的主题切换入口。
- 统一游戏数据层与美术生成器中的宝石色彩角色，保留主色、深底、描边和高光的必要差异。
- 整理样式中的历史注释与实际尺寸差异，补充手机横屏、竖屏和原生端的视觉验收基准。

建议的演进方向：**保留皇家商会主题，以更清晰的数字、更舒适的操作尺寸和更一致的材质精度提升品质。**

## 11. 扩展新主题与开局选择的架构可行性

### 结论

**可以基于现有架构实现。规则引擎、单页三屏与视图模型可复用。基线版本尚未具备多主题能力；本工作区已完成的实现见第 12 节。**

在保留牌桌布局、规则和资源语义的前提下，属于中等范围的表现层与设置改造。若新主题还需要不同桌面布局、镜头或完整世界观文案，则涉及更广的视图模型、动画坐标与日志呈现调整。

### 现有可复用基础

| 基础 | 代码证据 | 对多主题的价值 |
| --- | --- | --- |
| 独立规则计算 | `utils/game-engine.js:51` 的 `createGame`；支付按资源 key、成本和红利计算 | 外观可与规则计算分开 |
| 稳定卡牌标识 | `utils/game-data.js:244` 生成固定 `id` 后才洗牌 | 可用卡牌 ID 映射各主题素材 |
| 统一视图模型 | `pages/index/index.js:1266` 的 `buildViewModel` | 可集中解析当前主题、卡面和显示参数 |
| 统一屏幕容器 | `pages/index/index.wxml:4` 的 `.viewport` 包含舞台与弹层 | 可在根容器挂主题类，覆盖三屏和弹层 |
| 已有开局设置 | `onQuickStart`、`onPickSoloSeats`、`onCreateRoom`、房间准备页 | 可接入主题缩略图与选中态 |
| 房间快照同步 | `utils/room.js:472` 的配置更新与 `cloudStartGame` | 可扩展房间统一主题，并在开局固定 |

### 主题系统改造点

1. **主题注册与解析。** 增加主题 ID、名称、缩略图、可用状态、素材映射和默认回退。主题选择只接收注册的 ID；旧配置、未知 ID 与缺图应回退到皇家主题。
2. **布局和皮肤边界。** 从现有 `index.wxss` 中划分共享布局 / 交互状态与主题配色 / 材质 / 字体。所有主题素材选择器也要带作用域，避免后加载主题覆盖其他主题。
3. **表现映射。** `cardVM` 当前直接生成 `photo-* / art-*` 并使用 `card.name`；`gemStyle` 和头像渐变也在 JS 内拼接。新主题必须同时覆盖 WXSS、生成美术与这些内联显示参数。
4. **状态生命周期。** `freshUI` 会在重开、退房和房间失效时重建界面状态。需要区分建房弹窗里的待确认选择、创建成功后的房间主题和本局固定的主题，并覆盖取消、重开、退房、重连路径。
5. **预览构建。** `preview/build.js:258` 的模块清单是手工列出的；新增主题模块必须注册到该清单并满足依赖顺序。当前 H5 模块解析按文件 basename 查找，多个目录下同名 JS 模块不能直接照搬常见打包器的用法。

推荐先用一个 `utils/theme.js` 维护注册和解析，根容器使用类似 `class="viewport theme-{{themeId}}"` 的主题类。美术生成器按主题分别生成带作用域的资源样式；继续共用原有卡牌、筹码、弹窗与事件绑定。

### 已确定：房主在创建房间时选择统一主题

2026-11-11 用户确定：**暂时由房主创建房间时选择主题。**

首期采用以下流程与状态约定：

1. 房主在「创建房间」弹窗中选择主题，展示名称、预览和选中态；默认值为现有皇家主题。
2. 点击「创建房间」时，将有效主题 ID 与人数、回合计时一起保存为房间配置。取消弹窗恢复原选择；云端创建失败时保留原房间号、主题和设置，提供重试入口。
3. 其他成员加入后自动使用房间主题，准备页展示主题名称；主题选择入口集中在建房时。
4. 创建后的房间主题保持固定，开局把相同主题 ID 带入本局显示元数据；同房间重开沿用该主题。
5. 断线重连按房间 / 本局记录恢复主题；离开房间时清除房间主题上下文。旧房间没有主题字段时回退到皇家主题，未知主题回退并提示；构建期缺少源素材则报错，阻止不完整主题进入产物。

配置流为：**建房主题草稿 → 已保存的房间主题 ID → 本局显示元数据 → 各客户端主题解析与渲染。** 主题不改变卡牌 ID、数值、资源 key 或规则计算。

多人链路不能只给本地 `room` 对象添加字段：`createRoom`、`cloudCreateRoom` 和 `cloudPullRoom` 都显式列出字段。本次实现将逻辑字段 `room.themeId` 编码到已有 `seats` JSONB 的固定房主席位 `seats[0].roomThemeId`，沿用现有数据库字段与 CAS；开局再固定到 `state.themeId`。加入、准备、改人数、重开和重连均保留该元数据，无需新增数据库列。

### 素材与包体边界

当前 `art.wxss` 约 1236.5 KB，包含内嵌图片。工程的 `tests/size-guard.js:25` 对单文件设置了 2 MiB 守卫，多个完整主题直接拼进原文件很容易触达该限制。

首期少量主题可采用独立生成文件、共享通用素材和压缩缩略图，逐个检查生成物及整体包体。拆文件只解决单文件尺寸，不会减少静态导入的总资源；更多主题再评估按需加载、缓存与失败回退。

主题注册表只保存轻量元数据与引用，图片数据不放进房间快照或页面反复推送的数据中。

### 完整世界观换肤的额外边界

卡牌对象目前携带 `name / art`，规则引擎会将 `card.name` 直接拼入日志；贵族标题和部分规则用语也与珠宝世界观绑定。因此若新主题还要改卡名、资源名称或世界观文案，需要增加表现映射和可重渲染的日志描述，才能保证卡面、动作展演、详情与历史记录一致。

首期建议保持卡牌 ID、成本、分数和资源 key 稳定，以同布局的配色、桌布、卡背、边框、卡图和动效参数构成主题契约。

### 实施验收重点

- 两个主题使用同一牌局、同一随机种子与动作序列，规则结果一致。
- 三屏、卡牌详情、预留卡、贵族、结算和动作展演使用正确主题，样式不串色。
- 选择 / 取消 / 开局 / 重开 / 退房 / 冷启动恢复的主题行为符合约定。
- 覆盖房主建房选主题、取消 / 创建失败重试、成员自动跟随、开局和重连，以及旧配置回退；同房间重开主题保持一致。
- H5 新模块、主题样式和素材全部被正确打包；所有生成物通过工程体积守卫，并验证微信原生端。

本节为架构决策；具体实现与验收如下。

### 操作流程与状态

- 首页「创建房间」弹窗显示四个主题预览，只有建房时可以选择；默认皇家商会。

- 创建失败时保留原房间号与设置并阻止提前开局。重试先读取房间：若前次写入已成功，恢复现有成员和版本；确认房间不存在时才重新写入，避免覆盖已加入成员。
